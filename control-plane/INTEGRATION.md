# Daemon integration contract v0.1

Canonical contract: [`../shared/openapi.yaml`](../shared/openapi.yaml). Paths below are relative to `/api`. JSON requests are capped at 256,000 bytes, have a 10-second body-read deadline, and reject unknown fields. IDs are UUIDs. Digests and opaque file IDs are 64 lowercase hex characters; the daemon must consistently use its chosen digest algorithm and canonical serialization. Only metadata is accepted: never send file text, decrypted diffs, key material, storage credentials, log output, MCP output, or secret values. Labels and reference names must not contain secrets either.

## Authentication and transport

Production has two HTTPS origins. `BUNKER_ORIGIN` serves human sessions and initial enrollment. `BUNKER_HOST_ORIGIN` requires actual client-certificate mTLS for every connection. Verify the gateway's server certificate using the OS trust store or an explicitly provisioned trusted CA; never disable validation. Private upstream URLs and gateway proof headers are not part of the daemon protocol.

1. An admin/operator creates `POST /tenants/{tenantId}/enrollments` with `{name}`. The response is `{token,expiresInSeconds:600}`. It is one-use and checked against database wall-clock time after obtaining its row lock.
2. The host generates a P-256 (recommended) or RSA 2048–4096 private key locally, then signs a PEM PKCS#10 CSR. Send `POST /enroll` to the **public** HTTPS origin with `{token,csr}`. Keep the key on the host; do not send it to Bunker. CSR size is capped at 16,384 characters. Production requires the CSR.
3. The 201 response is `{hostId,tenantId,transport:"mtls",certificate,trustChain,expiresAt}`. `certificate` is a PEM clientAuth leaf with server-assigned `urn:bunker:tenant:<tenantId>:host:<hostId>` SAN. `trustChain` is the configured issuing CA PEM bundle. This is client-identity trust material, not permission to replace the daemon's gateway/server trust roots. Validate the issued certificate matches the local public key and assigned identity, and persist it with the key in protected host storage. No bearer token is returned in production.
4. Connect to the **host** HTTPS origin using the leaf, chain where needed, and local private key. Present no human cookie or gateway header. Host credentials grant only host actions in their enrolled tenant. The gateway verifies TLS chain/expiry/purpose/possession; Next additionally checks the exact registered fingerprint, tenant, host, and revocation on each request. A CA-signed but unregistered certificate does not authenticate.
5. Before the maximum 24-hour certificate expires, use valid mTLS to `POST /tenants/{tenantId}/hosts/{hostId}/certificate` with `{csr}` for a new locally generated key. The response has the same shape as production enrollment and retains the host ID. Only that host may renew. Old leaves remain usable until expiry or revocation, allowing atomic local credential replacement. Expired/revoked credentials cannot renew. An ambiguous response can be retried while the old credential remains valid; this issues another registered leaf. Hosts must schedule renewal and handle expiry safely; the Rust bridge is a separate workstream.

Administrator `POST /tenants/{tenantId}/hosts/{id}/revoke` revokes the host and all its certificates as well as its development bearer. Subsequent requests fail even on previously established TLS sessions. Revocation is enforced at the application layer; there is no CRL/OCSP endpoint. Key loss/expiry requires administrator-led new enrollment (new host ID), with policy reassignment and old-host revocation.

Development only: with `BUNKER_ALLOW_INSECURE_LOOPBACK=true` and an HTTP loopback origin, `{token}` enrollment still returns `{hostId,tenantId,token,transport:"development-loopback"}`. Subsequent requests use `Authorization: Bearer ...`. This is not mTLS and must remain loopback-only.

Human local authentication remains `POST /auth/login` `{email,password}`, with HttpOnly SameSite=Strict eight-hour sessions, exact Origin checks for mutations, and existing login throttling/RBAC. Federated sign-in begins with `GET /auth/providers`, then `POST /auth/federated/{provider}/start` with matching Origin. Navigate to the returned `authorizationUrl`. The browser receives a five-minute HttpOnly Secure SameSite=Lax flow cookie; the provider returns to the exact configured callback. `GET /auth/federated/{provider}/callback?code=...&state=...` consumes the flow, verifies the provider identity, and returns 303 with the regular session cookie to the configured origin. OIDC uses state, nonce and S256 PKCE; GitHub OAuth uses state and S256 PKCE and binds the numeric `/user` ID. No auto-link by email, no user creation, and no provider tokens exposed to the browser.

Instance-admin linking: first provision the user and tenant membership using existing administration; independently verify the provider's immutable subject. Run `pnpm --filter @bunker/control-plane identity:link link PROVIDER SUBJECT USER_UUID` with protected provider configuration and database access. The command refuses an existing binding. Use `unlink` with the same arguments to remove the binding and revoke all sessions for that user. Tenant roles remain local; provider email/group/role claims do not grant access.

## Host reporting and polling

Use `/tenants/{tenantId}` as the prefix:

- `GET /policies`: array containing zero or one effective policy `{id,body,version,updated_at}`; host override wins over tenant default. Poll every 30 seconds. Empty means no assigned policy, not success. Enforce capability/residency requirements locally; reject unsupported settings rather than silently downgrading them.
- `POST /snapshots`: `{id,agent,sessionId,manifestDigest,fileCount,totalBytes,capturedAt,status}`. `agent` is `claude-code|cursor|codex|copilot|kiro`; `status` is `succeeded|failed`; timestamps are ISO UTC strings. Identical retries are accepted; changing metadata for an existing ID returns 409. Host can only read its own snapshots.
- `POST /alerts`: `{eventId,type,severity,snapshotId,count}`. `snapshotId` may be null. Types: `mass-delete|force-push|history-rewrite|mcp-change|skill-change|backup-failed|backup-missed|restore-test-failed`; severity `warning|critical`. Reuse `eventId` for retries; this increments occurrences without creating a duplicate alert. Acknowledgment remains intact for retries of the same event. New events need new IDs. Detection and thresholds are host responsibilities.
- `POST /evidence`: `{id,snapshotId,finishedAt,sandbox,agents,mcps}`. Sandbox `container|temp-directory`; agents `[{agent,passed}]`; MCPs `[{name,passed}]`. No process output. At least one agent result is required. Any failed result atomically creates a `restore-test-failed` alert. Duplicate evidence IDs return 409; retrieve the existing row before deciding whether a retry succeeded.
- `GET /snapshots`, `/restores`, `/alerts`, `/evidence`: arrays of database envelopes containing `id`, `tenant_id`, `host_id`, `body`, and timestamps (plus workflow-specific fields). Latest 200, descending creation time. `?before=<ISO timestamp>` gets older records; equal-timestamp cursor pagination is not yet implemented. `GET /{resource}/{id}` returns a zero-or-one-element array. Human members see tenant records; hosts only their own records.

UI polling is every 15 seconds. This supports sub-minute visibility under a running service, but no end-to-end latency SLA has been validated.

## Restore approval protocol

1. The daemon computes and displays a decrypted local diff. Freeze the exact restore plan: snapshot manifest, target scope, destination mapping, prior destination hashes, planned after hashes, and deletions. Hash the canonical complete plan into `diffDigest`. The server cannot verify how the daemon computed it.
2. `POST /restores` with `{snapshotId,kind,manifestDigest,diffDigest,changes}`. `kind` is `file|session|workspace`. Each change is `{fileId,action,beforeDigest,afterDigest,bytes}` with opaque hashed file identity, `create|replace|delete`, nullable before/after hashes, and nonnegative byte count. At most 1,000 unique changes; file restore requires exactly one. Manifest must match a successfully reported snapshot owned by the requesting host. Return `{id,status:"pending"}`. Requests expire 15 minutes after creation. Creation is not idempotent; retain the returned ID and avoid blind retries after an ambiguous response.
3. An **independently authenticated human** admin/approver inspects the local content diff, reviews its metadata in the UI, and confirms the same digest. `POST /restores/{id}/decision` accepts `{decision:"approve"|"deny",diffDigest,reviewedLocalDiff}`. Approval requires `reviewedLocalDiff:true`. This is a human attestation, not remote proof that a local diff was viewed. Operators, viewers, and host credentials cannot decide.
4. The host polls `GET /restores`. An `approved` status is **not** an execution grant. Recompute the plan and validate destination before-hashes, then call `POST /restores/{id}/claim` with `{diffDigest}` immediately before execution. It atomically changes `approved` to `executing` and returns `{id,status:"executing",diffDigest,manifestDigest,expiresAt}`. Only the creating host can claim. Pending/denied/expired/already-claimed requests return 409. Concurrent claims have one winner.
5. Only the successful claim response permits one execution of that exact plan. Verify expiry and all bindings locally; stop if the destination changed, if the request was denied/expired, or if connectivity/response is ambiguous. **Never retry execution after an ambiguous claim.** There is intentionally no claim replay/reset endpoint. An `executing` request left by a crash requires investigation and a new human-reviewed request, not automatic replay.
6. Report `POST /restores/{id}/complete` with `{status:"succeeded"|"failed",diffDigest}`. Only the host with the claimed request can complete. Human decisions, claims, completions, and expired requests are audited. Expiration is materialized on subsequent tenant activity; there is no background expiry worker yet. Denied and expired requests never become executable.

The UI does not execute or stream decrypted local restores. **The daemon bridge must be integrated separately.** The control plane cannot constrain an already-compromised host or prove that host-reported execution/evidence is truthful. Never make the agent's local approval mechanism a substitute for independent human authentication.

## Human administration

Roles: `admin` (all human actions), `operator` (enrollment/policies/alert acknowledgment), `approver` (restore decisions), `viewer` (read/export). All members can view tenant evidence. Admins may create a client tenant in their own organization with `POST /tenants/{tenantId}/tenants {name}`; only the creating admin receives initial membership. Admins grant/update tenant roles through `/members {email,role,password?}`. An initial password is required only for a new account. This endpoint cannot reset existing passwords or change the caller's own role.

`POST /policies` upserts by nullable `hostId`. Includes schedule, retention, exclusions, cap, immutability, DR, residency, storage/key **reference labels**, detection thresholds and restore-test interval. `channels` defaults to `["ui"]`; `["ui", "webhook"]` explicitly opts in to the operator-provisioned signed webhook. UI remains required. Other channels and tenant-submitted destinations are rejected. See [webhook delivery](WEBHOOKS.md) for transactional semantics, receiver verification and the human-only delivery-status endpoint. Agent-scoped policy assignments are not yet implemented.

`POST /alerts/{id}/acknowledge` requires admin/operator. `GET /audit` exposes tenant audit history to humans only. `GET /export` downloads tenant snapshot, restore-test, policy, and audit metadata (latest 10,000 per category). The report states its cap and that it is not a compliance certification.

Errors use `{error,issues?}`. 400 validation; 401 authentication; 403 role/Origin/tenant; 404 missing or invisible resource; 408 body timeout; 409 stale/duplicate/conflicting state; 413 oversized; 415 content type; 429 login throttling; 501 obsolete `/auth/oidc` entry point; 503 unavailable database/transport/configuration. Rejected transactions commit no metadata changes. Treat unknown/unavailable states as a stop, never success.
