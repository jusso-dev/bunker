# ADR 0003: verified TLS gateway and explicit federated identities

Status: implemented locally; deployment and live provider validation remain outstanding.

Next route handlers expose HTTP requests, not verifiable TLS client-certificate state. Certificate headers supplied by a proxy or caller are therefore insufficient proof of host identity. Bunker uses a Node HTTPS gateway with two listeners. The public listener serves browsers and initial enrollment without requesting a client certificate. The host listener requests and requires a certificate, with `rejectUnauthorized: true`, TLS 1.2 minimum, and the configured host CA. OpenSSL verifies the certificate chain, validity, clientAuth purpose, and private-key possession. No TLS verification bypass is used.

Both listeners remove incoming Bunker, forwarded, client-certificate, SSL, and hop-by-hop headers. They buffer bounded request bodies and generate short-lived HS256 JWTs using `jose`, binding the method, exact normalized path/query, SHA-256 body digest, security-relevant headers, certificate fingerprint (or null), issue/expiry times, audience, issuer, and random nonce. Next verifies this proof and atomically consumes its nonce in an independent PostgreSQL transaction before handling the request. Failures in the API transaction do not make the proof replayable. All production HTTPS API requests require this proof. The public listener can never assert a host fingerprint.

The private upstream is restricted by gateway configuration to numeric loopback HTTP. Next must also bind only to loopback, share a machine/network namespace with the gateway, and be inaccessible from ingress. Process/file permissions separate the gateway from the signing key and provider credentials. The shared 32-byte gateway key is a protected binary file; compromise of either process or that key is outside this boundary. All replicas need the same replay database, synchronized clocks, and a coordinated key rotation/restart. This implementation intentionally does not support a cleartext remote upstream.

The host generates its own key and signed PKCS#10 CSR. `@peculiar/x509` validates the CSR signature; only P-256 or RSA 2048–4096 keys are accepted. Bunker ignores requested names/extensions, assigns a tenant/host URI SAN and clientAuth-only usages, and signs a maximum 24-hour leaf using a configured P-256 CA key. Signing failure rolls back one-use enrollment. Only certificate fingerprints recorded with their tenant and host authenticate. Revocation checks both host and leaf on every request. A valid host may submit a new CSR to renew its certificate with the same host ID; old leaves remain valid until expiry or administrator host revocation. There is no automatic daemon renewal implementation in this workstream, OCSP/CRL service, external signing service, HSM integration, or unexpired-certificate recovery mechanism after key loss.

OIDC uses `oauth4webapi` discovery, authorization code, S256 PKCE, state, nonce, issuer/audience/expiry checks, and explicit JWKS signature verification (RS256). Discovery and provider calls require HTTPS with normal TLS validation and reject redirects. Entra requires an exact tenant-specific issuer; Google uses its exact published issuer. GitHub consumer sign-in is OAuth, using its fixed authorization/token/user endpoints and stable numeric user ID; it is not treated as OIDC. GitHub uses state and PKCE, with no invented ID-token nonce validation.

Sign-in only finds an existing explicit `(provider, issuer, subject)` binding. It never creates users or links email claims. Instance administrators provision a local account/membership and link the externally verified subject through the CLI. Tenant admins cannot modify global identity bindings, preventing takeover of a user with memberships in other tenants. Unlinking revokes all of that user's sessions. Federated sessions use the existing cookie, tenant membership checks, CSRF checks, and RBAC. Callback state is browser-bound, expires after five minutes, and is consumed once before provider exchange, including failed exchanges.

Local trusted-loopback bearer development remains explicitly opt-in. Tests use disposable keys, a trusted local CA, actual HTTPS/mTLS, PostgreSQL, and local provider fixtures. They do not establish live Entra/Google/GitHub onboarding, production signing/provisioning, deployment isolation, availability, or Rust daemon interoperability. Root will independently arrange council review before PR work.
